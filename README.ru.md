# pixel-eub

CLI для загрузки совместимого Tensor Pixel из **Pixel ROM Recovery**
(чёрный экран, USB `18d1:4f00`, последовательный CDC-порт) в bootloader fastboot.
По умолчанию программа передаёт подписанные этапы в RAM по запросам ROM и проверяет результат
через `fastboot devices` и `getvar product`. Разделы телефона не прошиваются,
разблокировка загрузчика и очистка данных не выполняются.

[English](README.md) · Русский

**Аппаратное тестирование исходной команды `boot`:** на одном физическом Pixel 6a проверены подключение
по USB и отправка образов (по сообщению пользователя). Успешный выход в bootloader
fastboot не подтверждён. Эта проверка не подтверждает
восстановление всех перечисленных моделей и версий загрузчика: нужны подходящие
подписанные образы, а ROM проверяет подписи и защиту от отката.

## Установка

Python 3.10+. [Android SDK Platform-Tools](https://developer.android.com/tools/releases/platform-tools)
с командой `fastboot` в PATH нужны для автоматического подтверждения результата,
а не для передачи образов ROM. Linux, macOS и Windows используют pyserial;
интеграционный тест с псевдотерминалом выполняется на Linux.

### Запуск без venv

В папке проекта есть исполняемый файл `pixel-eub`. Он использует `python3`
из PATH и исходники рядом с собой; установка самого проекта не требуется.

```sh
chmod +x pixel-eub
./pixel-eub --help
./pixel-eub boot --device "Pixel 7 Pro" --pack auto --wait
```

Нужен Python 3.10+ с установленным `pyserial`. Проверить зависимость можно командой:

```sh
python3 -c 'import serial; print(serial.__version__)'
```

Также можно запускать `python3 pixel-eub ...` или `python3 -m pixel_eub ...`
из папки проекта. Для запуска из другой папки укажите полный путь к `pixel-eub`.
В Windows используйте `py pixel-eub ...`.

### Установка в venv (необязательно)

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
pixel-eub --help
```

Windows PowerShell: `py -m venv .venv`, затем
`.\.venv\Scripts\Activate.ps1` и `python -m pip install -e .`.
Без активации можно запускать `.venv/bin/pixel-eub` или
`.venv\Scripts\pixel-eub.exe`. Также доступен `python -m pixel_eub`.

## Быстрый запуск

```sh
pixel-eub detect
pixel-eub boot --device "Pixel 8 Pro" --wait
```

Если телефон ещё не появился: отключите его, удерживайте Power + обе кнопки
громкости, подключите USB и продолжайте удерживать примерно 15 секунд.
Команда `--wait` ждёт появления устройства до 60 секунд;
`--wait-timeout 120` меняет это время.

**Pixel 7, 7 Pro и Fold (возможно 7a):** держите все три кнопки, пока ROM не
запросит **BL1**, и отпускайте только после запроса DPM — лог подскажет.
По сообщениям пользователей, если первым приходит запрос DPM, телефон уже
запустил BL1 из внутренней памяти (UFS); такой BL1 ломает связь с GSA/GSC
при старых recovery-образах: цепочка зависает после BL3B и грузится с ошибками.
Поэтому для Pixel 7, 7 Pro и Fold pixel-eub в этом случае останавливается до
любой загрузки и просит переподключить телефон; `--allow-dpm-first` позволяет
продолжить. На Pixel 7a выводится только предупреждение. Для Pixel Tablet есть
отчёты об успешных сессиях, начинающихся с DPM, поэтому проверка не применяется.

В выводе последовательно появляются три фазы: `[1/3]` — проверка USB-соединения
с ROM Recovery, `[2/3]` — передача запрошенных `.img`, `[3/3]` — итоговая
проверка bootloader fastboot. Во время передачи сразу выводятся ROM identity,
запрос этапа, размер загрузки, завершение отправки и ACK телефона.
По умолчанию порядок этапов задаёт ROM. Исключение — явно подтверждённая
экспериментальная цепочка после iROM-паники с `--override`, описанная выше.

`--device husky`, `--device "Pixel 8 Pro"` и `--device pixel-8-pro`
равнозначны. `pixel-eub models` показывает известные названия и статус пакетов.

```sh
# Прочитать семейство чипа из ROM и предложить выбор модели в терминале:
pixel-eub boot --wait

# Выбрать порт при нескольких устройствах:
pixel-eub boot --device husky --port /dev/ttyACM0
pixel-eub boot --device husky --port COM3

# Подготовить и проверить источники без открытия USB:
pixel-eub boot --device husky --dry-run
```

ROM сообщает **семейство чипа, а не точную модель**. Без `--device` программа
показывает только модели обнаруженного семейства и предлагает выбрать одну.
В неинтерактивном запуске неоднозначность заканчивается ошибкой с подсказкой.
Несовпадение выбранного SoC с ROM останавливает передачу до первого загрузчика.
Разрешить попытку после явного подтверждения можно флагом `--override`.

## Диагностика и справка

Команда `./pixel-eub doctor` выполняет проверку зависимостей, прав
на ROM USB-порт, наличия fastboot, доступа и свободного места для кэша,
а также вспомогательных утилит Linux. Для своих путей используйте
`--fastboot PATH` и `--cache-dir PATH`. Команда не открывает телефон и ничего
не меняет. Код 1 означает отсутствие pyserial, недоступный порт или непригодный
путь кэша; отключённый телефон и отсутствие необязательных утилит не считаются
ошибкой. `./pixel-eub -h` показывает аргументы всех команд,
а `./pixel-eub boot -h` — только параметры восстановления.

## Графический интерфейс (Linux)

```sh
./pixel-eub gui
```

Необязательное окно на GTK 4 / libadwaita покрывает все команды CLI:
восстановление с живым прогрессом фаз и стадий, выбор recovery-пака и
заводских образов, `doctor`/`detect`, анализатор образов (`inspect`), полный лог и все
настройки. Каждое действие запускает тот же CLI в дочернем процессе, а точная
команда видна на странице Terminal, поэтому поведение и проверки безопасности
совпадают. Вопросы YES/NO превращаются в диалоги, где по-прежнему нужно ввести
`YES`. Переключатели override, чужого пака и восстановления порта действуют
только в текущем сеансе и не сохраняются. В GUI пароль администратора
для восстановления порта запрашивает системное окно polkit (`pkexec`); сам GUI
пароль не видит. С udev-правилом запрос не нужен вовсе.

Нужны PyGObject, GTK 4 и libadwaita 1.6+ из пакетов дистрибутива (не pip):
`sudo dnf install python3-gobject gtk4 libadwaita` в Fedora или
`sudo apt install python3-gi gir1.2-gtk-4.0 gir1.2-adw-1` в Debian/Ubuntu.
Для CLI они не нужны. Чтобы добавить пункт в меню приложений, скопируйте
`data/io.github.hurmichov.PixelEub.desktop` в `~/.local/share/applications/`,
а `pixel_eub/gui/icons/hicolor` — в `~/.local/share/icons/`.

## Реальная совместимость

| Модели | Семейство | Источник для EUB |
| --- | --- | --- |
| Pixel 6 / 6 Pro / 6a | gs101 | Публичного USB BL1 в закреплённом релизе нет |
| Pixel 7 / 7 Pro | gs201 | Общий recovery-пакет gs201 |
| Pixel 7a / Fold / Tablet | gs201 | Пакет соседней модели, нужен `--allow-experimental` |
| Pixel 8 / 8 Pro | zuma | Отдельные recovery-пакеты shiba / husky |
| Pixel 8a | zuma | Пакет husky, нужен `--allow-experimental` |
| Pixel 9 / 9 Pro / 9 Pro XL / 9 Pro Fold / 9a | zumapro | Нет публичного пакета; ROM ID здесь не подтверждён |
| Pixel 10 / 10 Pro / 10 Pro XL / 10 Pro Fold | laguna | Нет публичного пакета; протокол не подтверждён |

Распознавание названия модели и скачивание её заводского образа не означают
поддержку EUB-восстановления. Автоматическая передача разрешена только для
наблюдавшихся ROM ID: `9845` → gs101, `9855` → gs201, `9865` → zuma.
Неизвестный ID не получает загрузчик.

Заводской BL1 обычно не имеет подписанного разрешения USB-загрузки.
`pixel-eub` проверяет этот флаг перед передачей BL1 и не пытается его менять:
изменение нарушит подпись. По умолчанию используются только образы
`sources/` из закреплённого
[tensor-usbdl v0.2.0](https://github.com/JoshuaDoes/tensor-usbdl/releases/tag/020).
Бинарники и скрипты из архива не запускаются.

Даже recovery BL1 может быть отклонён защитой от отката. В частности, Google
описывает повышение anti-rollback для Pixel 6/8 в обновлении мая 2025 года
на [странице заводских образов](https://developers.google.com/android/images).
Последняя заводская сборка не делает старый recovery BL1 совместимым с новым
уровнем защиты. По умолчанию `bl1 header fail`, `eub:nak` и `irom_booting_failure`
завершают попытку с ошибкой. Релиз tensor-usbdl v0.2.0 заявляет поддержку
Pixel 8 / 8 Pro только с загрузчиком не новее апреля 2025; на более новых
пользователи получают `bl1 header fail`, и pixel-eub пишет об этом в ошибке.

По сообщениям пользователей (проектом не проверено):

- После GSA1 (иногда после BL3B) телефон может молчать 2–5 минут и дольше,
  пока идёт проверка, — это нормально. pixel-eub ждёт до `--ack-timeout`
  секунд (по умолчанию 600) и периодически сообщает о ходе ожидания.
- Перед прошивкой зарядите телефон минимум до 4200 мВ: ниже `fastboot flash`
  завершался ошибкой. После подтверждения fastboot pixel-eub выводит напряжение.
- Pixel Tablet может остановиться на BL31, не дойдя до fastboot: удерживайте
  Power около 30 секунд, пока он не пропадёт из USB, и повторите попытку.

## Заводские образы и выбор сборки

```sh
# Все официальные сборки нужной модели, SHA-256 и ссылки:
pixel-eub builds --device "Pixel 8 Pro"

# Скачивание последней общей стабильной сборки:
pixel-eub fetch --device husky

# Конкретная сборка, например из списка builds:
pixel-eub fetch --device husky --build AP1A.240505.005

# Также сохранить заводской образ при подготовке восстановления:
pixel-eub boot --device husky --build AP1A.240505.005 --wait
```

Каталог читается с официальной страницы Google по HTTPS. SHA-256 берётся из
той же строки таблицы, что и ссылка. `latest` выбирает новейшую сборку по дате
в build ID, исключая строки с дополнительными региональными/операторскими
оговорками; при неоднозначности нужен полный `--build`.
Загрузка образов подчиняется условиям Google, ссылка выводится до скачивания.
Заводской ZIP может занимать несколько гигабайт.

В `boot` приоритет источников: `--dir` → recovery-пакет → заводской FBPK.
Поэтому `--build` **не заменяет** подписанный USB BL1 и не гарантирует, что
все передаваемые этапы взяты из этой заводской сборки. Заводской ZIP остаётся
в кэше для последующей обычной прошивки и заполняет недостающие этапы.
Инструмент не запускает `flash-all` и не выполняет `fastboot flash`.

## Явное разрешение несовместимого пака

```sh
# Пример намеренного выбора gs201-пака для устройства семейства gs101:
pixel-eub boot --device "Pixel 6" --pack gs201 --override --wait
```

`--pack` принимает также имена `gs201`, `zuma/shiba` и `zuma/husky`:
выбранный набор читается из закреплённого recovery-архива в кэше, независимо
от `--device`. Без `--override` несовпадение модели/SoC отклоняется.

С `--override` программа показывает фактический и ожидаемый SoC либо
несовпадающие метаданные образа и запрашивает `YES/NO`. Только полный ответ
`YES` (регистр неважен) разрешает продолжить. `NO`, пустой или другой ответ
и конец ввода отменяют попытку до передачи загрузчиков.
При совпадающих устройствах лишний вопрос не появляется.
Для проверки SoC телефон сначала опрашивается без передачи образов;
подтверждение запрашивается при закрытом порте, после чего программа заново
подключается к тому же устройству и отвечает на свежие запросы ROM.
Одно и то же несовпадение подтверждается один раз за запуск.

Флаг разрешает несовпадение выбранной модели с ROM, известного recovery-пака
с моделью, а также модели/платформы в имени и метаданных FBPK. Разбиение EPBL
определяется по фактическому известному SoC телефона; `--epbl` имеет приоритет.
Смена телефона, неизвестный ROM ID, повреждение ZIP/FBPK, CRC/SHA-256,
отсутствующий подписанный USB-флаг BL1 и отказ ROM не обходятся.
Пример выше не означает, что gs201-загрузчик сможет запуститься на gs101:
проверки подписи и anti-rollback выполняет сам телефон.
Произвольные каталоги `.img` без метаданных не всегда позволяют установить SoC;
для стандартных каталогов `gs201` и `zuma/{shiba,husky}` используется их имя.

### Экспериментальное продолжение после паники

Флаг `--override` при `irom_booting_failure` после завершённой отправки
вызывает вопрос `Continue uploading despite the ROM panic? [YES/NO] (NO):`.
После полного `YES` программа отправляет оставшуюся **экспериментальную цепочку
без новых запросов ROM и без C**: после BL1 сразу PBL, затем остальные этапы.
План выводится до подтверждения. Пустой ответ, NO, другой ответ или EOF отменяют
попытку. Для этого порядка нет подтверждённого аппаратного результата; данные могут быть отвергнуты
или проигнорированы. PBL передаётся как EPBL (и EPBB при разбиении), дальнейшие
образы — отдельными заголовками/телами. Необязательные образы добавляются только
по подписанным тегам. Выбор появляется и после переподключения, когда
ROM печатает только hex-диагностику и панику без нового identity: программа
предупредит об использовании ранее проверенного identity сессии и дождётся YES.
Порт повторно ищется по исходным USB serial/location либо пути узла, если USB
идентификаторов нет. Это не новая проверка ROM identity: оставьте подключённым
тот же телефон. Если новый identity всё же пришёл и изменился, отправка запрещена.
`header fail` и NAK по-прежнему останавливают попытку; без `--override` паника
также завершает работу. Успех требует итоговой проверки fastboot.

## Кэш и работа без сети

```sh
pixel-eub boot --device husky --cache-dir ./cache --dry-run
pixel-eub boot --device husky --cache-dir ./cache --offline --wait
pixel-eub builds --device husky --refresh
```

Путь по умолчанию: `$PIXEL_EUB_CACHE`, иначе `$XDG_CACHE_HOME/pixel-eub`
или `~/.cache/pixel-eub` в Linux, `~/Library/Caches/pixel-eub` в macOS,
`%LOCALAPPDATA%\pixel-eub` в Windows. `--cache-dir` имеет приоритет.
Каталог сборок обновляется раз в сутки; `--refresh` запрашивает обновление.
В режиме `--offline` сеть не используется даже с `--refresh`.

Каждый сохранённый ZIP повторно проверяется по SHA-256 перед использованием.
Новые загрузки пишутся во временный файл и атомарно публикуются после проверки.
Незавершённые или повреждённые файлы не принимаются. Повторное скачивание
целого проверенного файла не требуется; прерванная загрузка начинается заново.

## Собственные источники

```sh
# Локальная копия закреплённого recovery-релиза:
pixel-eub boot --device husky --pack ./tensor-usbdl-v0.2.0.zip

# Собственный набор полных подписанных stage images:
pixel-eub boot --device husky --dir ./signed-stages --pack none

# Локальный заводской ZIP или bootloader*.img без recovery-оверлея:
pixel-eub boot --device husky --image ./factory.zip --pack none

# Проверить контейнер FBPK v2 и CRC32 его разделов:
pixel-eub unpack ./bootloader-husky-example.img
```

Последний вариант `boot --pack none` работает только для этапов, которые ROM
допускает: обычный retail BL1 будет отклонён локальной проверкой USB-флага.
Если телефон начал диалог уже с позднего этапа, ненужный BL1 не передаётся.
`--dir` ожидает целые образы, содержащие заголовок 4096 байт и тело,
а не заранее разделённые `STAGE.bin`. При `--dir` автоматический пакет
отключается; локальный `--pack PATH` можно добавить явно.

FBPK проверяется на платформу, распознанные имена продуктов, границы записей,
пересечения, CRC32 и противоречащие друг другу образы слотов. ZIP читается
без распаковки на диск. Имена файлов не могут переопределить подписанный тег
этапа: это особенно важно для GSA1/GSAF, имена которых в некоторых пакетах
переставлены. Локальные наборы выбирает пользователь; SHA-256 из официального
каталога для них отсутствует, а подписи по-прежнему проверяет телефон.

## Диагностика

- `detect --all`: показать все последовательные порты и USB ID.
- `inspect ФАЙЛ...`: описать образы стадий, FBPK, заводские ZIP и recovery-паки —
  стадию, подписанный флаг USB-загрузки и семейство SoC (известно только для
  ключей из закреплённого пака). Удобно для образов из неизвестных источников:
  BL1 без флага USB не загрузится по USB, а ручная установка флага ломает подпись.
- `--verbose`: печатать сообщения ROM; серийный номер попадёт в вывод.
- `--fastboot /path/to/fastboot`: выбрать установленный Platform-Tools.
- `--fastboot-serial SERIAL`: выбрать целевой fastboot для итоговой проверки.
- `--reconnect-wait 30`: дольше ждать смены USB-порта после BL2.
- `--verify-timeout 30`: дольше ждать подтверждения fastboot.
- `--ack-timeout 900`: дольше ждать ROM после загрузки стадии (проверка GSA1/BL3B).
- `--dump-usb ПАПКА` (Linux, для исследования): при каждом подключении ROM
  сохранять USB-дескрипторы (`.bin` и расшифровку в `.txt`) и писать в лог, что
  изменилось с прошлого подключения, например после BL1 или BL2. Данные читаются
  пассивно из sysfs, куда их записало ядро при подключении: без root, без
  выгрузки драйвера и без обращений к телефону. В файлах есть серийный номер USB —
  замажьте его перед публикацией. `detect --dump-usb ПАПКА` делает то же для
  найденных сейчас портов.
- `--capture ПУТЬ` (для исследования): записывать каждый байт от ROM и каждую
  загрузку (длина, первые 64 байта, SHA-256) с метками времени и номером
  подключения в формате JSON lines; `ПУТЬ` может быть папкой. Прошивки целиком
  не сохраняются.
- Если вместе с `irom_booting_failure` ROM присылает дамп ошибки, pixel-eub
  выводит его одной строкой: код, статус, значение и адрес. По наблюдениям на Pixel 6a
  `0x400` — отвергнут заголовок или тег, `0x500` — USB-загрузка не разрешена,
  `0x600` — не сошлась подпись или ключ. Это гипотеза по трём попыткам, а не
  документированное поведение.
- `--listen-after-failure СЕКУНДЫ` (для исследования): после
  `irom_booting_failure` ещё столько секунд читать порт и отмечать каждый повтор
  строки ошибки (время и первое слово) и другие сообщения ROM. Ничего не
  отправляется; запуск всё равно завершается ошибкой.
- `--no-usb-check`: всё равно отправить BL1 без подписанного флага USB-загрузки,
  только для экспериментов. ROM сам проверяет этот флаг как часть подписи и,
  скорее всего, ответит `bl1 header fail`; образ уходит только в RAM.
- `--epbl full|split`: явно выбрать разбиение EPBL для известного чипа.
- `--checksum sum16`: использовать сумму байтов вместо обычного `ffff`.
- `--port-recovery`: включить автоматическое восстановление доступа к порту (по умолчанию выключено).

Linux, только с `--port-recovery`: при `Permission denied` программа повторно проверяет USB ID порта
(`18d1:4f00`) и запрашивает через `sudo` ACL-доступ `rw` текущему пользователю
к конкретному узлу `/dev/ttyACM*`. Это не делает порт доступным всем пользователям.
Нужен `setfacl` (пакет `acl`); пароль администратора может потребоваться в терминале.
Если порт занят (`EBUSY`/`EAGAIN`), программа получает список владельцев через
`fuser` (пакет `psmisc`), выводит PID и посылает `SIGTERM` процессам,
удерживающим только этот порт, затем повторяет открытие.
Завершение этих процессов прервёт их собственную работу с данным телефоном.
Команды привязаны к этому узлу порта; настройки служб и драйверов не изменяются.
Если завершённый процесс обслуживал несколько устройств, его завершение
может повлиять и на них.
Текущая команда и её родительские процессы защищены от завершения.
Если прав по-прежнему нет после ACL, программа не пытается лечить это
завершением процессов и сообщает об ошибке. Без `--port-recovery`
ни одно из этих действий не выполняется; `--no-port-recovery` по-прежнему
принимается и имеет приоритет. Без терминала в графическом сеансе вместо `sudo` используется `pkexec`:
пароль спрашивает системное окно polkit. Без терминала и без графического
сеанса используется `sudo -n` без запроса пароля.

Для постоянного доступа можно настроить serial-группу (`dialout` или `uucp`
в зависимости от дистрибутива) либо udev-правило для `18d1:4f00`.
ModemManager может повторно захватывать порт после перезапуска; в таком случае
добавьте для данного устройства udev-исключение `ID_MM_DEVICE_IGNORE`.

Разрыв связи после BL2 — ожидаемый переход между этапами; программа ищет тот
же USB serial/location и заново сверяет ROM serial перед загрузкой.
При переподключении приоритет имеет последовательный ROM-порт: следующие
этапы передаются по запросам телефона до итоговой проверки fastboot.
Если утилита `fastboot` отсутствует или не работает, передача образов всё равно
выполняется. После завершения ROM-сессии программа сообщает, что результат
не подтверждён, и возвращает код `1`; экран телефона нужно проверить вручную.
Программа вообще не обращается к `fastboot` до завершения передачи по ROM.
Поэтому до загрузки нет снимка ранее подключённых fastboot-устройств: оставьте
подключённым один целевой телефон или укажите `--fastboot-serial SERIAL`.
При нескольких fastboot-устройствах автоматический выбор запрещён.
Разрыв сам по себе успехом не считается. Если recovery ABL сообщает `product: unknown`,
программа не может подтвердить выбранную модель и завершится с диагностикой,
даже если на экране уже есть fastboot.

Коды выхода: `0` — команда завершена успешно (для `boot` без `--dry-run` это
подтверждённый bootloader fastboot), `1` — ошибка/неподтверждённый результат,
`2` — ошибка аргументов, `130` — прерывание пользователем.

## Проверки и источники

```sh
python -m unittest discover -v
python -m pip install ruff
ruff check pixel-eub pixel_eub tests
ruff format --check pixel-eub pixel_eub tests
```

Тестируются парсеры, повреждённые образы и кэш, выбор сборок, отказ при другом
SoC/телефоне, повторы запросов, короткие записи, ошибки ROM, переподключение,
отсутствие ложного успеха и CLI с реальным pyserial на Linux PTY.
Тесты не требуют телефона или сети.

Сведения о протоколе: [JoshuaDoes/tensor-usbdl](https://github.com/JoshuaDoes/tensor-usbdl),
сопоставление с [hack-different/pixel-restore](https://github.com/hack-different/pixel-restore).
Формат FBPK сверялся с
[официальным fbpack.py](https://developers.google.com/android/binary_transparency/tools/pixel/fbpacktool/fbpack.py).
Подробности сообщений и фреймов — в [docs/protocol.md](docs/protocol.md).
Исходный код этой реализации — MIT; прошивки не включены и имеют собственные
условия распространения. Поддержка конкретного телефона подтверждается только
аппаратной проверкой.
